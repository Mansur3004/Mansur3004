Границы достоверности
--------------------
Изучены все присланные скриншоты tech_questionnaire_status, включая ветки,
приоритеты, сдвиг времени, UNION и финальный JOIN для RK. Пользователь подтвердил:
под tech_questionnaire_rk имелся в виду tech_questionnaire_status со скриншотов.
Прототип использует уже созданные RK из связи с клиентом, как в этом скрипте.
Восстановлена кредитная часть для КН/КК/авто. ДК, депозиты и текущие счета — вне
согласованного объёма итоговой витрины; их продуктовые макросписки не скопированы.

Полные списки промежуточных атрибутов ниже соответствуют текущему SQL; состав
проверен исполнением на пустой синтетической БД. Типы приведены к PostgreSQL
по выражениям и известным типам источников, не получены из банковской БД.
RAW: все 62 атрибута из предоставленного списка; BDM: 66 видимых атрибутов
(3 длинных имени на скриншоте обрезаны и явно помечены многоточием).
TAS: все 22 атрибута показанного DDL. Связь анкета–клиент: показаны только 3
необходимых атрибута; полный состав этой таблицы НЕ предоставлен.

В каждой секции TABLE указаны ВСЕ выходные атрибуты соответствующего шага,
их типы и выражения первого SELECT. При UNION атрибуты выровнены по порядку;
для второго плеча см. SQL. Алиасы раскрываются через список "Читает" и SQL.
Расчётные поля и служебные номера обозначены выражениями, не выданы за RK.

1. КАК В RAW ПОЯВЛЯЕТСЯ ПРОДУКТ
-----------------------------
В RAW level25_product_bp_nm отсутствует. После очистки prt_tqs_questionnaire:
  КК: (src_cd_src LIKE &p_quest_src_cd_kk_list OR product_type_code IN
       (&p_quest_product_kk_list)) AND length(questionnaire_id) NOT IN
       (&p_quest_not_len_id_kk_list). Ветке присваивается &p_prod_kk_name.
  КН: (src_cd_src LIKE &p_quest_src_cd_kn_list OR product_type_code IN
       (&p_quest_product_kn_list)) AND src_cd_src NOT LIKE
       &p_quest_src_cd_kk_list. Ветке присваивается &p_prod_kn_name.
  Авто: src_cd_src LIKE &p_quest_src_cd_ak_list OR product_type_code IN
       (&p_quest_product_ak_list). Ветке присваивается &p_prod_auto_name.
Это константа ветки, а не JOIN со справочником и не однозначное соответствие
источника продукту. Сохранены оба плеча OR, исключение КК из КН и SQL-семантика
NULL: KN с NULL src_cd_src не проходит NOT LIKE. Если ветки пересекаются,
исходный UNION ALL сохраняет обе строки; маршрутизация видна в отчёте 4.11.
Далее q.src_cd не фильтруется, продукт проверяется по level25_product_bp_nm.
В оригинальном TQS src_cd = RAW.src_cd_src; RAW.src_cd сохранён как raw_src_cd.

    TAS.application_rk -> detail.tas_application_rk. BDM.application_rk служит ключом соединения; он не подменяет отсутствие TAS. -1 -> NULL.

    TAS.application_dt -> detail.tas_application_dt. Не заменяется датой анкеты/BDM.

    TAS.agr_signed_flg -> detail.tas_agr_signed_flg.

    COALESCE(TAS.level25_product_bp_nm, TQS.level25_product_bp_nm). При несовпадении приоритет TAS, оба исходных значения сохранены в detail; конфликт показывает отчёт 4.15.
18. level35_product_bp_nm | text
    COALESCE(TAS.level25_product_bp_nm, TQS.level25_product_bp_nm), как для уровня 25. Пользователь подтвердил совпадение логики уровней. Для анкеты без TAS оба уровня берутся из TQS. Исходный TAS.level35 сохранён в detail для диагностики.
19. processed_dttm | timestamp(0)
    CAST(&p_report_timestamp AS timestamp(0)): момент текущей загрузки, один на запуск; не максимум времён источников.

Флаги заявок — поля TAS, уже прошедшие её собственный ETL. Здесь они не
пересчитываются из bdm.application_status. При нескольких разных непустых
значениях TAS на одном ключе спорное поле = NULL, исходные строки и счётчики
конфликтов сохраняются в адаптерах. NULL второй стороны соединения не заменяем
false/1900/-1. processed_dttm финала относится к этому прототипу.

Гранулярность результата — найденное соответствие текущей анкеты и сущности
TAS либо несвязанная сторона. N:M сохранены, один RK может быть в нескольких
строках. Пометки RK в перечне полей не являются доказательством уникальности
отдельного поля или ограничением PRIMARY KEY: у несвязанных сторон ключи NULL.

5. ЧТО ЕЩЁ НУЖНО ПОЛУЧИТЬ И ГДЕ
-------------------------------
A. Название скрипта уточнено пользователем: tech_questionnaire_status со скриншотов.
Отдельный tech_questionnaire_rk не требуется. Как в исходнике, используется
настоящий RK из tech_questionnaire_x_customer, без подмены row_number.

Если один RK связан с несколькими ID, исходный LEAD строит общую историю
по RK; в текущий срез попадёт действующая версия ID. Исторические ID остаются
в prt_qas_tech_questionnaire_status, номера и флаг объединяются по RK/продукту.
Такие связи показывает отчёт 4.17. Для авто используется равенство текущего
questionnaire_id и application_id; при ненулевом отчёте 4.17 нужно подтвердить
кардинальность и смысл связей в исходном tech_questionnaire_x_customer.

B. Для полного каталога связи анкета–клиент: DBeaver -> схема dm_pik_fd_cdmr ->
tech_questionnaire_x_customer -> Columns и DDL. Нужны весь список столбцов,
типы, ключи и правила актуальности. Скриншоты подходят, копировать код не нужно.
Для BDM на той же вкладке уточнить 3 обрезанных длинных имени.

C. Правило уровня 35 подтверждено пользователем: его логика полностью
совпадает с уровнем 25. Отдельный справочник не требуется. Оба итоговых поля =
COALESCE(TAS.level25_product_bp_nm, TQS.level25_product_bp_nm), включая анкеты
без TAS. Исходные уровни TAS и продукт анкеты сохранены в detail; расхождения
показывает отчёт 4.15, равенство итоговых уровней проверяет prt_qas_checks.

D. Для актуальности TAS: Columns/DDL и последняя выборка её ETL, чтобы подтвердить
актуальный снимок или назвать реальный effective_to-фильтр. По processed_dttm
актуальность не угадывается. Для выбора DIRECT/UZ нужны результаты отчёта 2.7,
для покрытия >=10% — отчёт 4.5 на реальных данных.

E. Показанная исходная формула сдвига использует EXTRACT(SECONDS), который
возвращает компонент секунд (61 секунда -> 1), а не полную длительность.
Скрипт сохраняет это поведение для сопоставимости; отчёт 4.14 показывает
затронутые строки и неположительные интервалы. При ненулевом результате
сравнить эти строки с оригинальным ETL перед изменением формулы.

Готовые read-only запросы для получения метаданных (либо открыть Columns):

select table_schema, table_name, ordinal_position, column_name, data_type,
       character_maximum_length, numeric_precision, numeric_scale, datetime_precision
from information_schema.columns
where (table_schema, table_name) in (
    ('rd_raw_orb', 'v_sn_all_mart_dapp_prod_dm_dsa_cd_questionnaire_x_intention'),
    ('bdm', 'application'),
    ('dm_pik_fd_cdmr', 'tech_questionnaire_x_customer'),
    ('sbx_pre_orb_fd', 'tech_application_status')
)
order by table_schema, table_name, ordinal_position;

select table_schema, table_name, ordinal_position, column_name, data_type,
       numeric_precision, numeric_scale, datetime_precision
from information_schema.columns
where table_schema = 'sbx_pre_orb_fd'
  and (table_name like 'prt_tqs_%' or table_name like 'prt_qas_%'
       or table_name = 'prt_tech_internet_funnel')
order by table_name, ordinal_position;

Локальная проверка не подтверждает банковские данные/Greenplum. Финальная
проекция, сохранность строк и всех исходных TQS-полей проверяются автоматически
на синтетических данных; реальные метаданные подтвердит запрос выше.
