УСЛОВИЯ НА ПЕРВОМ СКРИНШОТЕ
--------------------------
OR level25 IS NULL + EXISTS добавлен, чтобы реализовать запасной продукт из
анкеты по ФТ: TAS без продукта включается только при конкретной связи с
целевой анкетой. В проверке 1 измеряется реальное использование этой ветки.
Если все целевые ветки ETL TAS гарантируют заполненный продукт, этот блок
избыточен; его можно убрать вместе с зависимыми допусками NULL-продукта.
Нулевой счётчик в одном запуске сам по себе не доказывает гарантию на будущее.

Условие хотя бы одного RK <> -1 исключает строку без реальной заявки.
Один родительский ключ без дочернего допустим. Это не удаление дублей.
Проверка 2 показывает, есть ли вообще такие строки среди целевых продуктов.

ШАГ 1.3 НЕ ГАРАНТИРУЕТ ОДИН НОМЕР НА QUESTIONNAIRE_ID
---------------------------------------------------
GROUP BY(questionnaire_id,application_num) делает уникальной только пару.
Строки (Q1,N1), (Q1,N1), (Q1,N2) превращаются в (Q1,N1), (Q1,N2).
Проверка 3 видит повтор одинаковой пары в RAW, проверка 4 — разные номера.
Если 4 не пуста, условие «один номер на анкету» в текущем мосте не выполнено.
Это отличается от взаимного 1:1: разные анкеты могут ссылаться на одну заявку.

ПРОВЕРЕНА ИСХОДНАЯ ЛОГИКА TQS
----------------------------
Фрагмент prt_tqs_questionnaire со скриншотов, сохранённый в истории Git
e5573dd:sql/build_internet_funnel_v3.sql, использует:
    ROW_NUMBER() OVER (PARTITION BY questionnaire_id,status ORDER BY ...)
    WHERE rn = 1
Следовательно, он оставляет одну исходную запись НА СТАТУС, не на всю анкету.
Разные статусы могут сохранить разные application_num. Само копирование этого
ROW_NUMBER не гарантирует один номер на questionnaire_id.
Затем оригинальный ETL строит версии статусов; TQS не публикует application_num.

Чтобы получить номер именно выбранной текущей записи TQS, нужно воспроизвести
выбор исходной записи для текущего статуса по его исходным приоритетам и проверить
соответствие текущей версии/продукту. Для этого требуются статус и поля порядка
из intention, а не только ID/номер. Полное повторение внутренних веток TQS
не требуется, но правило источника для этого моста должно быть согласовано.
Нельзя молча подменять его MAX(application_num), свежайшей строкой по одной
произвольно выбранной дате или ROW_NUMBER только по ID.
Если в данных один номер на ID уже выполняется, дополнительный выбор не нужен.

Для ID, найденного проверкой 4, можно отдельно посмотреть исходные записи:
    select questionnaire_id, application_num, status,
           createtime_dttm, processed_dttm, sessionintention_id
    from rd_raw_orb.v_sn_all_mart_dapp_prod_dm_dsa_cd_questionnaire_x_intention
    where questionnaire_id = 'ЗАМЕНИТЬ_НА_ПРОБЛЕМНЫЙ_ID'
    order by createtime_dttm desc, processed_dttm desc, status, application_num;
Это просмотр причин, не новое правило выбора последней строки. Имена полей
взяты из показанного исходного ETL; прототип TIF их по-прежнему не читает.

РАЗНЫЕ ПРИЧИНЫ КРАТНОСТИ
-----------------------
Проверка 3: одинаковая пара ID/номер повторена в RAW. Это может быть нормальной
историей источника; по двум полям нельзя установить, чем отличаются полные строки.
Проверка 4: разные номера одной анкеты. Нужны проверка реальных строк и правило выбора,
если бизнес требует один номер. Это не повтор одной и той же пары.
Проверка 5: повтор текущего RK/источника BDM — проверить контракт версионности BDM.
Проверка 6: один номер в одном источнике ведёт в несколько BDM RK.
Проверка 7: несколько путей к одному BDM RK. Нужно разложить по номерам и исходным строкам.
Проверка 8: несколько разных дочек одной УЗ. Такая 1:N может быть корректна.
Проверка 9: повтор той же итоговой пары перед GROUP BY в matches; сверить входы TAS/BDM/TQS.
Проверка 10: неоднозначная текущая строка TQS; устранение после JOIN скроет исходную проблему.
Проверка 11: неоднозначность текущей строки по ID, даже если разные RK сами по себе уникальны.

ЧТО ОСТАВЛЯТЬ В ПРОТОТИПЕ
------------------------
MAX(CASE) в историческом флаге — содержательная агрегация по истории, её сохраняем.
Группировки отношений в 1.3, 1.4, 2.1 были заложены без измерения реальной
кратности. Их необходимость определяется результатами этих проверок.
ROW_NUMBER уместен при согласованном выборе одной версии исходной записи;
он не является универсальной заменой GROUP BY и не исправляет неверный JOIN.
Если нужен только факт существования связи, EXISTS позволяет избежать
размножения из-за нескольких путей, сохранив все реальные заявки.
Нельзя выбирать одну дочернюю заявку по ROW_NUMBER на родителе или анкете,
пока ФТ допускает несколько разных заявок.
