# Новый порядок скрипта

Порядок задан пользователем: **верификация анкеты → КН/КК → автокредиты**.
Сейчас реализуется первый блок. Блоки связей не выбираем и не объявляем
проверенными до получения результатов первого блока и проверки атрибутов.

## 1. Общий флаг верификации анкеты

Готовы `sql/status_by_product.sql` и
`sql/workflow/01_questionnaire_verification.sql`. Источник — техническая TQS,
заявки и BDM на этом этапе не нужны.

| Шаг | Создаваемая таблица | Что делаем |
| --- | --- | --- |
| 1.0 | `prt_qs_status_by_product` | Справочник кандидатов из жёлтых строк на скриншотах |
| 1.1 | `prt_qs_verification_params` | Фиксируем момент отчёта |
| 1.2 | `prt_qs_verification_policy` | Задаём продукт, источник, смысл флага и подтверждённость правила |
| 1.3 | `prt_qs_verification_history` | Забираем историю статусов, отмечаем совпадения со справочником |
| 1.4 | `prt_qs_verification_facts` | Агрегируем до одной строки на ключ анкеты |
| 1.5 | `prt_qs_verification_decisions` | Отделяем подтверждённые true/false от недостатка сведений |
| 1.6 | `prt_qs_verification_flags` | Готовим общий флаг для присоединения к обеим веткам |
| 1.7 | запросы контроля | Проверяем уникальность, неопределённые правила и неизвестные продукты |

Рабочая гипотеза — «анкета хотя бы раз достигла выбранного статуса».
Режим `CURRENT_STATUS` тоже предусмотрен. «Верификация успешно пройдена»
потребует согласованного набора статусов успешного завершения. Эти смыслы
не взаимозаменяемы.

Кандидаты из жёлтой заливки:

| Продукт | Источник TQS | `status_cd` | Что непосредственно видно |
| --- | --- | --- | --- |
| КН | `1376%` | `одобрено`, `CHECK_LIST_EMPTY` | Одобрение; связь с верификацией не подтверждена |
| КК | `1383%` | `DONE` | Название статуса «Выдача»; связь с верификацией не подтверждена |
| Авто | `1388%` | `VERIFICATION`, `DEAL_VER` | Статусы проверки; успешное завершение не подтверждено |

Цветовая легенда не предоставлена. Таблица фиксирует наблюдения, не ФТ.
По умолчанию результат бизнес-флага `verification_flg` — NULL, а
`verification_candidate_flg` показывает срабатывание гипотезы. Изменение
списков статусов не требует менять группировку, ветки или финальное объединение.

Зерно общего результата — `(questionnaire_rk, src_cd)`. Исследуем, действительно
ли этот ключ устойчив для истории TQS. Дубликаты статусов не создают несколько
строк флага. Неизвестный продукт или конфликт ключа остаётся диагностикой.

Для «хотя бы раз» сначала читаем историю, затем агрегируем. Фильтр
`effective_to_dttm = '2999-12-31'` до агрегации потерял бы ранее достигнутые
статусы. Для текущего статуса предварительно используем интервал `[from, to)`
на `report_dttm`. Проверить семантику интервалов по фактическому ETL.
Нельзя объявлять историю полной только по наличию нескольких строк в TQS.

## 2. Ветка КН/КК — только после проработки флага

Блоки будущего SQL в том же стиле. Это план запросов, не выполненный ETL.

```sql
-- 2.1. Берём анкеты КН/КК из источника questionnaire_status,
-- где есть application_num; сохраняем questionnaire_id и src_cd.
drop table if exists sbx_pre_orb_fd.prt_qas_kn_kk_questionnaire;
-- create table ... with (...) as select ... distributed randomly;

-- 2.2. Находим устойчивый мост от этих строк к ключам технической TQS.
-- В DDL TQS application_num не показан: не обращаемся к выдуманной колонке.
drop table if exists sbx_pre_orb_fd.prt_qas_kn_kk_questionnaire_keys;
-- create table ...;

-- 2.3. Присоединяем готовый общий флаг по questionnaire_rk + src_cd.
drop table if exists sbx_pre_orb_fd.prt_qas_kn_kk_questionnaire_flags;
-- create table ...;

-- 2.4. По application_num находим BDM-заявки, получаем application_rk.
drop table if exists sbx_pre_orb_fd.prt_qas_kn_kk_bdm_application;
-- create table ...;

-- 2.5. Проверяем прямой продуктовый путь и путь через УЗ до TAS.
drop table if exists sbx_pre_orb_fd.prt_qas_kn_kk_link_candidates;
-- create table ...;

-- 2.6. Сравниваем покрытия, степени связей и конфликты.
drop table if exists sbx_pre_orb_fd.prt_qas_kn_kk_link_quality;
-- create table ...;

-- 2.7. Фиксируем подтверждённые пары выбранного пути.
drop table if exists sbx_pre_orb_fd.prt_qas_kn_kk_links;
-- create table ...;

-- 2.8. Сохраняем связанные пары, анкеты без заявки и заявки без анкеты.
drop table if exists sbx_pre_orb_fd.prt_qas_kn_kk_fin;
-- create table ...;
```

Фильтры: КН TQS `1376%`, продуктовые заявки `MSCL`; КК TQS `1383%`, заявки
`CCPP_CRCA`/`CCPP_BATR`; УЗ в BDM — `MSSA`. Для BDM со скриншотов известно
`effective_to_date = DATE '2999-12-31'`; границу периода нужно согласовать.
Сначала отбираем когорту и текущий срез, затем выполняем внешние соединения.

Новые скриншоты показывают ETL через `bdm.application_x_application`:
`parent_application_rk` УЗ → `child_application_rk` продуктовой заявки,
с фильтрами актуальности, `application_application_link_type_cd` и источника.
Значение макроса `P_APPLICATION_LINK_TYPE` ещё не показано. Это подтверждает
структуру родительской связи, но не гарантирует покрытие связи с анкетами.

Для сравнения нужны:

- продуктовый `bdm.application.application_rk = tas.application_rk`,
  с согласованными источниками ключа;
- УЗ `bdm.application.application_rk = tas.parent_application_rk`,
  где `tas.parent_src_cd = 'MSSA'`, а дочерний источник соответствует продукту.

Особенности TAS, теперь видимые в ETL:

- УЗ без дочерней заявки сохраняется с `application_rk = -1`,
  `application_id = NULL`, `src_cd = NULL`. Источник УЗ — `parent_src_cd`.
  Фильтр только по `tas.src_cd` потеряет такие строки.
- Дочерняя заявка без УЗ получает `parent_application_rk = -1`.
- `-1` — отсутствие соответствующей сущности, не ключ для соединения.
  Нельзя связывать все строки с `-1` друг с другом или выкидывать строку
  УЗ только из-за отсутствия дочернего ключа.
- Статусное `parent_approved_flg` принудительно повышается при наличии
  дочерней заявки; это не флаг верификации анкеты.
- `final_approved_flg`/`agr_signed_flg` дополняются по сделке. Они также
  не подменяют верификацию без отдельного требования.

Поэтому старый `sql/03_probe_full_paths.sql` — ранний диагностический прототип,
его адаптер TAS надо пересмотреть на этапе 2. Сейчас не запускаем его как
финальную сборку и не переносим его фильтр дочернего источника на все TAS.

## 3. Ветка автокредитов — после КН/КК

```sql
-- 3.1. Берём текущие анкеты авто с источником 1388% и проверенным продуктом.
drop table if exists sbx_pre_orb_fd.prt_qas_auto_questionnaire;
-- create table ...;

-- 3.2. Присоединяем ТОТ ЖЕ общий флаг по questionnaire_rk + src_cd.
drop table if exists sbx_pre_orb_fd.prt_qas_auto_questionnaire_flags;
-- create table ...;

-- 3.3. Берём заявки авто из TAS: src_cd = 'ALPP'.
drop table if exists sbx_pre_orb_fd.prt_qas_auto_application;
-- create table ...;

-- 3.4. Проверяем questionnaire_id = application_id и уникальность пар.
drop table if exists sbx_pre_orb_fd.prt_qas_auto_links;
-- create table ...;

-- 3.5. Сохраняем связанные пары и обе стороны без пары.
drop table if exists sbx_pre_orb_fd.prt_qas_auto_fin;
-- create table ...;
```

В TAS на показанных скриншотах нет поля окончания действия. Актуальность
надо подтвердить контрактом пересборки либо реальным полем версии;
`processed_dttm` не используется как автоматическая замена.

## 4. Итог — после обеих веток

```sql
-- 4.1. Объединяем две ветки по единому явному списку колонок.
drop table if exists sbx_pre_orb_fd.prt_qas_fin;
-- create table ... as ... union all ... distributed randomly;

-- 4.2. Контролируем сохранность анкет/заявок, уникальность пар и флага,
-- обе стороны без пары и покрытие уникальных сущностей по каждой ветке.
```

«10% от всей базы» оцениваем отдельно по уникальным анкетам и заявкам и
по объединённому числу сущностей. Число строк INNER JOIN может расти из-за
N:M и не служит единственным критерием. До согласования смысла порога это
диагностические показатели, а не автоматическая приёмка.
