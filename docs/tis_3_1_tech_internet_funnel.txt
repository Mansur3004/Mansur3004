3.1. Описание процесса формирования сквозной воронки интернет-продаж по кредитным продуктам (TECH_INTERNET_FUNNEL)

В объекте dm_pik_fd_cdmr.TECH_INTERNET_FUNNEL содержится информация о прохождении анкетами и заявками этапов кредитного процесса по продуктам «Потребкредит», «Кредитные карты» и «Автокредит»: от создания анкеты и прохождения верификации до оформления заявки, одобрения, подписания договора и выдачи кредита.

Витрина объединяет данные готовых объектов TECH_QUESTIONNAIRE_STATUS и TECH_APPLICATION_STATUS. В результате сохраняются связанные пары «анкета — заявка», анкеты без найденной заявки и заявки без найденной анкеты. Наличие даты выдачи и прохождение всех промежуточных этапов не являются обязательными условиями включения записи в витрину.

Объект срезный, неверсионный. При обновлении хранится актуальный результат расчёта; история предыдущих состояний TECH_INTERNET_FUNNEL не ведётся. Атрибут processed_dttm содержит единое время текущей загрузки.

Основные источники данных:
- dm_pik_fd_cdmr.tech_questionnaire_status — ключ, идентификатор и дата анкеты, продукт, история статусов и текущий срез анкет;
- rd_raw_orb.v_sn_all_mart_dapp_prod_dm_dsa_cd_questionnaire_x_intention — идентификатор анкеты questionnaire_id и номер заявки application_num; дополнительные поля используются при выборе исходной записи;
- bdm.application — соответствие номера заявки ключу application_rk и системе-источнику src_cd;
- dm_pik_fd_cdmr.tech_application_status — ключи родительской и дочерней заявок, даты и признаки прохождения этапов, продукты 25 и 35 уровней бизнес-плана.

Наполнение витрины выполняется с 01.01.2025. Обновление производится ежедневно после успешного обновления используемых источников. Период пересчёта начинается с первого числа предыдущего квартала, но не ранее 01.01.2025. Данные за пределами периода пересчёта сохраняются загрузчиком. История статусов TQS, необходимая для определения прохождения верификации, используется целиком в доступном объёме, включая статусы до начала пересчитываемого периода.


Формирование анкетной части

Анкетные атрибуты отбираются из текущего среза dm_pik_fd_cdmr.tech_questionnaire_status со следующими условиями:
- level25_product_bp_nm in ('Потребкредит', 'Кредитные карты', 'Автокредит');
- effective_to_dttm = timestamp '2999-12-31';
- questionnaire_rk is not null и questionnaire_rk <> -1;
- questionnaire_dttm >= начало пересчитываемого периода либо questionnaire_dttm is null.

Из TQS переносятся questionnaire_id, questionnaire_rk, questionnaire_dttm и level25_product_bp_nm. Дата анкеты берётся из текущей записи готового источника. Повторная очистка анкет, определение продукта и построение интервалов версий TQS внутри TECH_INTERNET_FUNNEL не выполняются.

Для каждой пары questionnaire_rk / level25_product_bp_nm по всей доступной истории TQS рассчитывается исходный флаг верификации. Флаг принимает значение true, если найден хотя бы один из следующих статусов соответствующего продукта:

Потребкредит:
- '0';
- '10.0';
- 'одобрено';
- 'CHECK_LIST_EMPTY';
- 'CHECK_LIST_ANTIFRAUD_OR_PRODUCT'.

Кредитные карты:
- 'DONE';
- 'COURIER'.

Автокредит:
- 'APPROVE_RKK';
- 'APPROVED';
- 'PRE_APPROVED';
- 'APPROVE_CALL2';
- 'APPROVE_CALL3';
- 'ORDER_CREATED';
- 'VERIFICATION';
- 'DRIVER_CARD_ISSUE';
- 'DRIVER_CARD_ISSUE_UPLOADED';
- 'DOSSIER_UPLOADED';
- 'DEAL_VER';
- 'CREDIT_ISSUED';
- 'PRODUCT_BASKET_SIGNED'.

Если согласованный статус не найден, исходный флаг равен false. После сопоставления с TAS наличие связанной заявки, включая найденную родительскую заявку без дочерней, устанавливает итоговый quest_verification_flg = true независимо от исходного флага. Если заявка не найдена, сохраняется значение, рассчитанное по истории TQS. Для строки заявки без найденной анкеты флаг равен NULL.


Подготовка номера заявки для Потребкредита и Кредитных карт

Для анкет КН/КК используется соответствие questionnaire_id / application_num из rd_raw_orb.v_sn_all_mart_dapp_prod_dm_dsa_cd_questionnaire_x_intention. Выборка ограничивается идентификаторами анкет, включённых в анкетную часть. Для перехода к BDM используются непустые номера заявок.

На questionnaire_id выбирается одна исходная запись с помощью ROW_NUMBER() и отбора rn = 1. Порядок приоритетов перенесён из подготовки исходных данных TQS. Раздел окна в TIF — questionnaire_id, без разделения по статусу: история статусов берётся из готовой TQS, а мосту требуется один номер на анкету.

Правило ранжирования кандидатов с непустым application_num:

ROW_NUMBER() OVER (
    PARTITION BY r.questionnaire_id
    ORDER BY
        COALESCE(CAST(r.createtime_dttm AS timestamp), TIMESTAMP '1900-01-01 00:00:00') DESC,
        r.sessionintention_id,
        COALESCE(CAST(r.processed_dttm AS timestamp), TIMESTAMP '1900-01-01 00:00:00') DESC,
        COALESCE(CAST(r.business_dt AS timestamp), TIMESTAMP '1900-01-01 00:00:00') DESC,
        r.utmcn DESC,
        r.utmcct DESC,
        r.utmcmd DESC,
        COALESCE(r.globalclient_id, '#') DESC,
        COALESCE(r.person_id, '#') DESC,
        COALESCE(r.last_nm, r.first_nm, r.middle_nm, '#') DESC,
        COALESCE(r.tax_payer_num, '#') DESC,
        COALESCE(r.email, '#') DESC,
        COALESCE(r.client_type, '#') DESC,
        COALESCE(r.company_nm, '#') DESC,
        CAST(CASE WHEN r.phone_num NOT LIKE ('%%%') THEN 1 ELSE 0 END AS integer) DESC,
        r.credit_amt DESC,
        r.zero_visits_flg DESC,
        r.product_type_code,
        COALESCE(CAST(r.questionnaire_dt AS timestamp), TIMESTAMP '1900-01-01 00:00:00') DESC,
        r.program_type,
        COALESCE(CAST(r.scoring_dt AS timestamp), TIMESTAMP '1900-01-01 00:00:00') DESC,
        COALESCE(CAST(r.prescoring_dt AS timestamp), TIMESTAMP '1900-01-01 00:00:00') DESC,
        r.application_num DESC,
        COALESCE(r.scoring_status_nm, '#') DESC,
        COALESCE(r.prescoring_status_nm, '#') DESC,
        COALESCE(r.spec_program, '#') DESC,
        COALESCE(r.src_cd_src, '#') DESC,
        r.salary_card_flg DESC,
        r.phone_num
) AS rn

В мост передаются questionnaire_id и application_num; поля ранжирования в итоговую витрину не переносятся. При отсутствии записи intention или заполненного номера анкета сохраняется в анкетной части. Дополнительный номер для неё не генерируется.


Подготовка заявочной части

Данные заявок отбираются из готового объекта dm_pik_fd_cdmr.tech_application_status. TAS хранит последнее состояние заявки; при изменении данных источника запись обновляется. История версий TAS внутри TECH_INTERNET_FUNNEL не восстанавливается.

Основной отбор выполняется по следующим условиям:
- level25_product_bp_nm in ('Потребкредит', 'Кредитные карты', 'Автокредит');
- COALESCE(application_dt, parent_application_dt) >= начало пересчитываемого периода либо результат COALESCE равен NULL;
- присутствует хотя бы один реальный ключ: parent_application_rk или application_rk отличается от NULL/-1.

Записи TAS без заполненного level25_product_bp_nm допускаются при наличии установленного соответствия целевой анкете: через родительский ключ и источник для КН/КК либо по идентификатору для Автокредита. Для такой связанной строки продукт 25 уровня может быть получен со стороны анкеты.

Из TAS переносятся:
- parent_application_rk, parent_application_dt;
- parent_open_flg, parent_prescoring_flg, parent_at_work_flg, parent_approved_flg;
- application_rk, application_dt, deal_issue_date;
- create_flg, at_work_flg, final_approved_flg, agr_signed_flg;
- level25_product_bp_nm, level35_product_bp_nm.

Атрибуты parent_src_cd и application_id используются для сопоставления. Даты и этапные признаки TAS переносятся без повторного расчёта.


Связь анкеты и заявки для Потребкредита и Кредитных карт

Выбранный номер заявки сопоставляется с bdm.application по условию:
    intention.application_num = application.application_num.

Используется текущая версия записи BDM:
    application.effective_to_date = date '2999-12-31'.

Полученные application_rk и src_cd определяют ключ и источник родительской заявки. Дата начала действия версии BDM не используется как дата создания заявки и не задаёт нижнюю границу этого поиска: родительская заявка может быть старше пересчитываемого периода.

Далее выполняется сопоставление с TAS по условиям:
    application.application_rk = TAS.parent_application_rk;
    application.src_cd = TAS.parent_src_cd.

Для ветки КН/КК используются строки TAS с level25_product_bp_nm in ('Потребкредит', 'Кредитные карты') либо с незаполненным продуктом при наличии указанной связи. Отдельного обязательного равенства продуктов анкеты и дочерней заявки в этом сопоставлении нет; продукт итоговой строки определяется по правилам заполнения level25_product_bp_nm.

Если родитель связан с несколькими дочерними заявками, сохраняется отдельная строка на каждую найденную пару «анкета — родитель — дочерняя заявка». Найденная родительская заявка без дочерней также сохраняется. Произвольный выбор одной дочерней заявки через ROW_NUMBER() не выполняется.


Связь анкеты и заявки для Автокредита

Для Автокредита используются текущие атрибуты анкеты из TQS и данные TAS. Сопоставление выполняется напрямую:
    TQS.questionnaire_id = TAS.application_id.

Анкета должна иметь level25_product_bp_nm = 'Автокредит'; строка TAS — тот же продукт либо NULL при найденной связи. Номер из intention и BDM.APPLICATION для этой ветки не используются. Если родительская заявка отсутствует, найденная дочерняя заявка сохраняется.


Формирование итогового набора и заполнение атрибутов

Сначала формируется анкетная часть через LEFT JOIN с найденными связями и атрибутами TAS. Все отобранные анкеты сохраняются, в том числе не имеющие номера заявки или соответствия в TAS.

Затем из подготовленной TAS добавляются только заявки, для которых пара parent_application_rk / application_rk отсутствует в сформированной анкетной части. Проверка выполняется через NOT EXISTS по обоим ключам. Отсутствующие заявочные ключи предварительно нормализуются к -1. Наличие другой дочерней заявки у того же родителя не препятствует добавлению несвязанной пары.

Анкетная часть и оставшиеся заявки объединяются через UNION ALL. Уже связанная заявка не добавляется повторно отдельной строкой без анкеты. Логическая идентификация строки результата выполняется по сочетанию questionnaire_rk / parent_application_rk / application_rk. Связь одной заявки с несколькими анкетами представляет несколько строк результата.

Основные правила заполнения:
- questionnaire_rk — ключ из TQS; для заявки без найденной анкеты — -1;
- questionnaire_dttm — дата/время из текущей строки TQS; для заявки без анкеты — NULL;
- quest_verification_flg — итоговый признак верификации по истории статусов и наличию связи; для заявки без анкеты — NULL;
- parent_application_rk и application_rk — соответствующие ключи TAS; при отсутствии сущности — -1;
- даты и признаки этапов родительской/дочерней заявки — значения TAS; для анкеты без заявки — NULL;
- level25_product_bp_nm — COALESCE(TAS.level25_product_bp_nm, TQS.level25_product_bp_nm);
- level35_product_bp_nm — собственное поле TAS.level35_product_bp_nm; при отсутствии заявки или значения — NULL;
- processed_dttm — единый момент текущей загрузки.

В результате присутствуют 19 атрибутов: questionnaire_rk, questionnaire_dttm, quest_verification_flg, parent_application_rk, parent_application_dt, parent_open_flg, parent_prescoring_flg, parent_at_work_flg, parent_approved_flg, application_rk, application_dt, deal_issue_date, create_flg, at_work_flg, final_approved_flg, agr_signed_flg, level25_product_bp_nm, level35_product_bp_nm, processed_dttm.


Особенности использования данных для анализа полной цепочки

Полная цепочка «анкета — заявка — выдача кредита» определяется наличием реальной анкеты, реальной дочерней заявки и заполненной даты выдачи:
- questionnaire_rk is not null и questionnaire_rk <> -1;
- application_rk is not null и application_rk <> -1;
- deal_issue_date is not null.

Эти условия применяются только при анализе полных цепочек, а не при формировании общего состава TECH_INTERNET_FUNNEL. Родительский ключ для Автокредита необязателен; дополнительное требование равенства всех этапных флагов true не задаётся. Единица подсчёта цепочек — различное сочетание questionnaire_rk / parent_application_rk / application_rk; одна анкета с двумя выданными заявками образует две цепочки.

Сопоставление и оценка полной цепочки зависят от заполнения источников:
- при отсутствии application_num у анкеты КН/КК связь через номер с BDM и TAS не формируется; сама анкета сохраняется в витрине. В проверенном срезе прототипа по Потребкредиту номер заявки преимущественно не заполнен;
- при отсутствии parent_application_rk либо совпадения ключа и источника родителя связь КН/КК с TAS не формируется. Совпадение источника без совпадения ключа не создаёт связь;
- при незаполненной deal_issue_date заявка сохраняется в витрине, но не учитывается как полная цепочка до выдачи. В проверенном срезе прототипа по Кредитным картам дата выдачи в TAS не заполнена, поэтому продукт не представлен в выборке полных цепочек по данному критерию. Само отсутствие даты не подтверждает отсутствие фактической выдачи.

Указанные наблюдения о заполненности относятся к проверенному срезу источников. При обновлении источников состав найденных связей и полных цепочек пересчитывается по тем же правилам.
