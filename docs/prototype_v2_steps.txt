ПОЧЕМУ УБРАНЫ ПРЕЖНИЕ 1.2 / 1.3 / 1.4
------------------------------------
В предыдущем варианте 1.2 отдельно разбирал даты, 1.3 материализовал причины
отбраковки, 1.4 выполнял ранжирование дублей. Это было разбиение подготовки
источника на добавленные таблицы. В V2 возвращён один исходный запрос TQS:
фильтрация, COALESCE/MIN и ROW_NUMBER находятся внутри нового 1.1.
ROW_NUMBER из исходного ETL не удалён: он выбирает запись по заданным там
приоритетам. Отдельные таблицы проверки и безопасного разбора дат удалены
только из НОВОГО варианта; старый файл не редактировался.
Нумерация V2 самостоятельная: его 1.2 и 1.3 — продуктовые ветки КК/КН,
1.4 — исходный расчёт времени статусов КН, а не прежние проверки.

СХЕМА
-----
КН/КК:
  RAW -> 1.1 очистка + WHERE только КН/КК
      -> 1.2 КК -------------------------+
      -> 1.3 КН -> 1.4 времена статусов --+-> 1.5 UNION -> 1.6 RK/история TQS
      -> 1.7 флаг верификации -> 1.8 BDM по application_num
      -> 1.10 пары с TAS из 1.9 -> 1.11 пары + обе несвязанные стороны.
Авто:
  готовая TQS -> 2.1 флаг -> 2.3 FULL JOIN с TAS авто из 2.2.
Объединение:
  1.11 + 2.3 -> 3.1 итог;
  3.2 -> 3.3 счётчики анкет; 3.4 -> 3.5 счётчики заявок -> 3.6 отчёт о связке.

ИСПРАВЛЕНИЕ ОТЧЁТА ПОСЛЕ ОШИБКИ HIGH VMEM USAGE
-----------------------------------------------
Greenplum отменил запрос с несколькими COUNT DISTINCT при превышении памяти
ресурсной группы. В сообщении показан общий расход группы, на него могут
влиять одновременно работающие запросы. Это не измерение памяти только
одного запроса. План выполнения банковского запроса в этой среде недоступен.

Переписан только блок показателей после готового итога. Вместо нескольких
одновременных DISTINCT — две последовательные группировки и два подсчёта.
Показатели точные, а не приближённые. SQL проверен на равенство прежнему
запросу, включая NULL, повторяющиеся пары и пустой вход. Основной ETL 1.1–3.1
и согласованные 19 бизнес-полей не менялись.

ШАГ 3.2 — Одна строка на RK анкеты и признак найденной связи.
SQL V2: строки 946–965. Результат: &db_sbx.prt_if2_coverage_questionnaires.
Откуда: расчёт покрытия готовой витрины, исправление ошибки VMEM.
Зачем: выполнить одну группировку/агрегацию за запрос вместо нескольких DISTINCT.
Копирование: новый расчёт показателей, не часть исходных TQS/TAS.

Из уже готового итога выбираются только questionnaire_rk и признак наличия
заявки. GROUP BY questionnaire_rk и MAX(CASE ... THEN 1 ELSE 0 END) дают одну
строку на анкету. Анкета считается связанной, если хотя бы одна её строка
связана. NULL RK исключается, как раньше в COUNT(DISTINCT questionnaire_rk).
Таблица распределяется по questionnaire_rk. Это узкий результат подсчёта,
к подготовке RAW/фильтрам бизнес-данных шаг не относится.

ШАГ 3.3 — Счётчики уникальных анкет из подготовленной группировки.
SQL V2: строки 966–982. Результат: &db_sbx.prt_if2_coverage_questionnaire_counts.
Откуда: расчёт покрытия готовой витрины, исправление ошибки VMEM.
Зачем: выполнить одну группировку/агрегацию за запрос вместо нескольких DISTINCT.
Копирование: новый расчёт показателей, не часть исходных TQS/TAS.

Считаются COUNT(*) и SUM(linked_flg) по 3.2. Результат всегда одна строка;
при пустом входе оба счётчика равны 0. DISTINCT больше не требуется,
потому что одна анкета уже представлена одной строкой.

ШАГ 3.4 — Одна строка на пару RK заявки и признак найденной анкеты.
SQL V2: строки 983–1002. Результат: &db_sbx.prt_if2_coverage_applications.
Откуда: расчёт покрытия готовой витрины, исправление ошибки VMEM.
Зачем: выполнить одну группировку/агрегацию за запрос вместо нескольких DISTINCT.
Копирование: новый расчёт показателей, не часть исходных TQS/TAS.

Вторая ветка отчёта читает готовый итог, группирует два bigint:
parent_application_rk, application_rk. Это та же сущность заявки, что была
в COUNT(DISTINCT ROW(...)). Группы с одним NULL ключом сохраняются; строки
без ОБОИХ RK исключаются, как в исходном CASE перед COUNT DISTINCT.
MAX признака непустого questionnaire_rk означает, что пара связана с анкетой.
Распределение — по ОБОИМ RK, чтобы один часто пустой parent_application_rk
не стал единственным ключом распределения.

ШАГ 3.5 — Счётчики уникальных заявочных пар из подготовленной группировки.
SQL V2: строки 1003–1019. Результат: &db_sbx.prt_if2_coverage_application_counts.
Откуда: расчёт покрытия готовой витрины, исправление ошибки VMEM.
Зачем: выполнить одну группировку/агрегацию за запрос вместо нескольких DISTINCT.
Копирование: новый расчёт показателей, не часть исходных TQS/TAS.

COUNT(*) и SUM(linked_flg) по 3.4 дают одну строку. При пустом входе оба
значения 0. Повторы исходных строк, статусов, номеров и N:M не увеличивают

ШАГ 3.6 — Итоговый отчёт о связке из двух однострочных таблиц счётчиков.
SQL V2: строки 1020–1033.
Откуда: прежние пять показателей отчёта покрытия, без изменения их смысла.
Зачем: соединить одну строку счётчиков анкет с одной строкой счётчиков заявок
и вычислить процент только после их подсчёта. Итоговый CROSS JOIN даёт одну
строку; никаких больших наборов DISTINCT в этом запросе нет.

Память на реальном Greenplum не измерена. GROUP BY тоже требует ресурсов,
поэтому это уменьшение одновременной нагрузки, а не гарантия прохождения при
любых квотах. Если ошибка останется, сравнить EXPLAIN группировок и проверить
с администратором нагрузку ресурсной группы, распределение данных и spill.
Настройки statement_mem, квоты и параллельность код не изменяет.
