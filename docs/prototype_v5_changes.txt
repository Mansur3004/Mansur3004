ЧТО ПЕРЕНЕСЕНО И СОКРАЩЕНО В INTENTION
------------------------------------
Из удалённого prt_tqs_questionnaire перенесён полный ORDER BY окна:
createtime_dttm DESC, sessionintention_id ASC, processed_dttm DESC,
business_dt DESC и все последующие исходные приоритеты без перестановок.
Источник сравнения: e5573dd:sql/build_internet_funnel_v3.sql, шаг 1.1,
подтверждённый ранее скриншотами исходного TQS.

Явная адаптация V5: PARTITION BY questionnaire_id вместо questionnaire_id,status.
Историю статусов хранит готовая TQS, мосту нужен один номер на анкету.
Непустые номера отбираются до окна; более свежая запись без номера не обнуляет мост.
Если приоритеты полностью совпали, application_num тоже одинаков, поскольку
он сам входит в исходный ORDER BY; выбор физической строки не меняет вывод моста.

Оставлены только выходные поля ID/номер и технический rn. Поля порядка читаются
для выбора исходной записи, но не выводятся в итог и не сохраняются отдельно.
Не возвращены: MIN даты анкеты, исходные классификаторы продукта/статуса,
разведение совпадающих дат, LEAD интервалов, UTM-атрибуты итогового объекта,
повторная очистка ФИО/периода RAW. Популяцию задаёт уже очищенная текущая TQS,
она проверяется через EXISTS. Это сокращённый мост, а не полный повтор ETL TQS.
Поэтому это адаптация выбора записи источника, а не обещание дословной
идентичности строки, выбранной полным ETL TQS для каждого статуса.

При текущем результате №4 новый выбор не должен менять найденный номер:
во всех повторных непустых записях одного ID он один и тот же.
Если позже появятся разные номера, V5 выберет один по полному порядку TQS;
это намеренное отличие от V4, сохранявшего все номера. Проверка 16 это выявляет.
Не утверждаем, что выбранная RAW-строка всегда соответствует текущему статусу TQS.

ЧТО ГАРАНТИРУЕТ «1 К 1»
----------------------
В questionnaire_numbers не более одной строки и одного непустого номера на ID.
Если номера нет, строки в мосте нет; анкета остаётся в основной базе TQS.
Это не взаимное соответствие всех сущностей: разные ID могут иметь один номер,
а у одной УЗ могут быть несколько разных дочерних заявок. Их не удаляем.
Если сама текущая TQS неоднозначна по ID/RK или готовая TAS повторяет свою пару
ключей, ROW_NUMBER в intention не исправляет эти отдельные нарушения.

ПОЧЕМУ ОБВЕДЁННЫЕ ФИЛЬТРЫ ОСТАЛИСЬ
---------------------------------
NULL-продукт + EXISTS: допускает TAS без собственного продукта только при связи
с целевой анкетой, чтобы COALESCE(TAS.level25,TQS.level25) мог взять продукт TQS.
Без NULL-ветки такая заявка отсечётся ещё до соединения и запасной продукт
не будет использован. В проверенном срезе таких строк нет, влияние равно нулю.
Убрать можно при гарантированно заполненном продукте во всех целевых ветках TAS;
одного нулевого результата для такого контракта недостаточно.

Хотя бы один RK <> -1: отбрасывает запись без реальной заявки. Это не дедупликация.
OR сохраняет случаи родитель без дочки и дочка без родителя. На проверенном
срезе фильтр не исключил строк; сохранён как явное определение заявочной стороны.

ОГРАНИЧЕНИЯ ПРОВЕРКИ
--------------------
Полный исходный ETL tech_application_status в доступных файлах/истории Git
не найден. Поэтому его ROW_NUMBER и приоритеты НЕ заявлены как перенесённые.
TAS читается как подтверждённый пользователем снимок последнего состояния;
processed_dttm не превращается в выдуманное правило выбора «последней версии».
Конфликтующие строки готовой TAS остаются видимыми в результате и проверке 2.

GROUP BY сохранён только для содержательного расчёта исторической верификации.
В диагностических SELECT он считает нарушения и покрытия, а не исправляет данные.
Локально проверены PostgreSQL-синтаксис и поведение на искусственных данных DuckDB;
новая V5 в банке ещё не запускалась, покрытие по продуктам не измерено.
