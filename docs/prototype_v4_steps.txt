ЧТО И ГДЕ МЕНЯЕТСЯ ОТНОСИТЕЛЬНО V3
----------------------------------
1. Шапка и P_BEGIN_DATE. ФТ 1.2, строка 1: начальное наполнение с 01.01.2025;
   ежедневно пересчитывается выборка с первого числа прошлого квартала.
   На 03.11.2026 эта дата — 01.07.2026. Её задаёт ETL/SQL-клиент:
   GREATEST(DATE '2025-01-01', DATE_TRUNC('quarter', report_timestamp)::date
                                 - INTERVAL '3 months').
   p_rds_report_dt_date ограничивает доступную историю RAW независимо от
   P_BEGIN_DATE. Историю для исторического флага не обрезать текущей версией.
   CTAS прототипа пересоздаёт выборку sbx. Он НЕ выполняет частичный DELETE
   целевой витрины. Начальную загрузку и сохранение старых данных вне окна
   реализует ETL целевого объекта. Правила затрагивания связей на границе
   окна также должны быть согласованы в загрузчике, а не заменены слепым
   удалением строк только по одной дате.

2. Шаги 1.1–1.7. Исходная очистка/дедупликация RAW, продуктовые ветки,
   приоритеты и перенос application_num сохранены. DISTINCT остаётся
   только в исходном SELECT DISTINCT шага 1.1. RK по-прежнему берётся
   из готовой TQS, не из TQXC. Исторический флаг рассчитывается до
   сворачивания истории в анкетную сущность.

3. Новые 1.8–1.10 вместо прежнего 1.8 с LEFT JOIN BDM.
   1.8 формирует одну анкету RK + продукт с MIN даты и MAX исторического
   флага, включая анкеты без номера. 1.9 формирует отношение
   (RK анкеты, продукт, application_num). 1.10 переводит номера в BDM RK.
   Несколько номеров одной анкеты, ведущих к одному BDM RK и источнику,
   сворачиваются GROUP BY по ключу отношения. Это не удаление дублей
   атрибутов TAS и не произвольный выбор одного номера/одной заявки.
   Дата создания родителя BDM не ограничивается датой когорты дочерней
   заявки: родитель может быть старше. Версия BDM — effective_to_date = max_date.

4. Новый 1.11 вместо прежнего 1.9 (TAS КН/КК).
   SELECT без DISTINCT. Строки и флаги TAS не агрегируются. Продукты
   отбираются по level25_product_bp_nm, а не предположению «один источник —
   один продукт». NULL-продукт TAS допускается при найденной связи
   с целевой анкетой: конечный продукт тогда берётся из анкеты по ФТ 1.4.
   Неидентифицированные несвязанные NULL-продукты не относятся к подтверждённой
   выборке трёх продуктов и не добавляются без правила классификации.
   Значения -1 сохраняются, NULL в двух заявочных RK заменяется на -1.
   Строки без обоих реальных заявочных ключей не включаются.

5. Новый 1.12 вместо прежнего 1.10. ФТ 1.2, строка 4 говорит:
       app.application_rk = tas.parent_application_rk
       app.src_cd = tas.parent_src_cd
   Agreement-ключей в этом условии нет. Удалены прямое соединение с
   tas.application_rk, отдельный путь собственного RK УЗ и условия по
   источнику дочерней заявки. Источники сравниваются для РОДИТЕЛЬСКОГО
   ключа. GROUP BY хранит одну запись отношения «анкета — пара ключей TAS»,
   не подавляя возможные конфликтующие строки самой TAS.

6. Новый 1.13 вместо прежнего 1.11. Анкеты LEFT JOIN найденные ключи,
   затем LEFT JOIN исходные строки TAS. В этой таблице есть только
   связанные анкеты и анкеты без заявки; заявок без анкеты ещё нет.
   Флаг при связи true; без связи — исторический флаг. Ключи отсутствующей
   стороны -1; даты и флаги отсутствующей стороны NULL. DISTINCT нет.

7. Авто, шаги 2.1–2.3. Сохранена история TQS для флага. Вход TAS теперь
   без DISTINCT. FULL JOIN заменён LEFT JOIN от анкет. Остаток TAS
   добавляется общей следующей веткой. По уточнению пользователя TAS хранит
   последнее состояние, поэтому временной JOIN не требуется. В 2.1 сначала
   агрегируется история, затем присоединяется текущий ID анкеты из TQS.
   Исторический ID не создаёт лишнюю анкетную строку и не соединяется с TAS.

8. Новые 3.1–3.3 вместо прежнего итогового 3.1.
   3.1: первая таблица man_prt_tif_questionnaire_funnel — обе анкетные ветки.
   3.2: man_prt_tif_remaining_tas — только строки TAS с NOT EXISTS в 3.1
        по ПОЛНОЙ паре (parent_application_rk, application_rk).
   3.3: UNION ALL первой таблицы и оставшихся заявок.
   Проверять только parent_application_rk нельзя: у одной УЗ могут быть
   разные дочерние заявки. Связанные заявки повторно не добавляются.
   UNION/DISTINCT вместо правильного NOT EXISTS не используется.

9. Проверки переписаны под V4, -1, новую связь и отдельные продукты.
   Числитель/знаменатель анкет классифицируются по продукту анкеты;
   числитель/знаменатель заявок — по исходному продукту TAS. NULL-продукт
   TAS выводится отдельной группой в обоих счётчиках. Счётчики разных
   сущностей нельзя делить друг на друга. Каждый SELECT выполняется отдельно.

ВЕРСИОННОСТЬ И УНИКАЛЬНОСТЬ ПО УТОЧНЕНИЮ ОТ 03.11.2026
-------------------------------------------------------
TAS хранит только последнее состояние заявки: при изменении источника
запись переписывается. Её ключ — parent_application_rk + application_rk.
Интервалы TAS и дополнительный выбор по processed_dttm не нужны.
В финале сохраняется актуальный результат, без версий статусных строк.

У TQS исторический ключ — questionnaire_rk + effective_from_dttm.
Поэтому один RK в разных версиях истории сам по себе не является дублем.
В шаге 2.1 MAX статусов и MIN даты сначала вычисляются по всей истории
RK + продукта; потом ID для связи берётся из среза effective_to_dttm = max_date.
Так подтверждённый историей флаг не теряется, а старые ID не создают
лишних связей/строк. Шаг 2.3 соединяет актуальный ID с готовым снимком TAS.
Вход КН/КК в 1.6 уже получал RK из актуального среза TQS, это сохранено.

LEVEL35 — СОБСТВЕННОЕ ПОЛЕ TAS
-----------------------------
В шагах 1.11 и 2.2 оба поля продукта уже читаются из TAS отдельно.
В конечных проекциях 1.13, 2.3, 3.2 теперь используется:
    cast(t.level35_product_bp_nm as text) as level35_product_bp_nm
Ни level25 источника, ни level25 анкеты в это выражение не подставляются.
Если в исходной TAS уровни заполнены одинаково, это свойство её ETL.
Прототип сохраняет реальные значения источника, включая различие уровней.
Без заявки или при NULL собственного поля TAS level35 остаётся NULL,
как в ФТ 1.4. Правило level25 с запасным значением из анкеты не изменено.
Шаги 3.1 и 3.3 только передают полученные поля в UNION ALL.
