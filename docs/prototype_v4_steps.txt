TIF V4 — УПРОЩЁННАЯ ЛОГИКА ОТ 05.11.2026
========================================
SQL: sql/build_internet_funnel_v4.sql.
Результат: &db_sbx.man_prt_tif_tech_internet_funnel, 19 полей.

TQS — готовый источник анкет. Его внутренние очистка, классификация продукта,
приоритеты статусов и построение effective_from/effective_to внутри TIF не выполняются.
TAS — готовый снимок последних состояний заявок. Его этапные флаги не пересчитываются.
questionnaire_x_intention — только связь questionnaire_id/application_num, больше полей из него нет.

ШАГ 1.1 — Исторический флаг по готовой TQS
---------------------------------------
Результат: man_prt_tif_verification.
Из TQS читаются questionnaire_rk, level25_product_bp_nm, status_cd.
MAX(CASE) по всей доступной истории даёт один флаг на RK/продукт.
Статусы и продукты задаются существующими макропеременными. Дата начала
когорты здесь не обрезает историю: иначе можно потерять ранее пройденную верификацию.

ШАГ 1.2 — Анкеты из готового текущего среза TQS
---------------------------------------------
Результат: man_prt_tif_questionnaire.
Из текущей строки TQS берутся questionnaire_id, questionnaire_rk,
questionnaire_dttm, level25_product_bp_nm; присоединяется флаг из 1.1.
Читается существующий effective_to_dttm = max_date. Новые интервалы не строятся.
Дату анкеты не вычисляем через MIN: берём уже рассчитанное значение TQS.
Отбор P_BEGIN_DATE применяется к дате готовой анкеты. NULL-дата, как прежде,
не исключается. Анкеты без RAW-записи и без номера остаются в этой базе.

ШАГ 1.3 — Два поля из questionnaire_x_intention
--------------------------------------------
Результат: man_prt_tif_questionnaire_numbers.
Читаются только questionnaire_id и application_num. EXISTS ограничивает
номера отобранными анкетами КН/КК, GROUP BY сворачивает одинаковые пары.
Все разные номера сохраняются. Фильтров по ФИО, датам RAW, статусам,
product_type_code или src_cd_src нет. Исходный TQS-процесс здесь не копируется.

ШАГ 1.4 — Анкета -> номер -> BDM.APPLICATION
-----------------------------------------
Результат: man_prt_tif_kn_kk_bdm.
TQS.id соединяется с парами 1.3, номер — с BDM.application_num.
Берутся актуальный application_rk и src_cd. Группируются только ключи
отношения: один результат через несколько номеров не размножается.
Родитель может быть старше дочерней заявки: его дата создания не ограничивает lookup.
Ненайденные анкеты не пропадают: полная анкетная база независимо сохранена в 1.2.

ШАГ 1.5 — Единый готовый снимок TAS
---------------------------------
Результат: man_prt_tif_tas.
Три продукта читаются из одной TAS без DISTINCT и без определения продукта по источнику.
NULL-продукт допускается при найденной связи с целевой анкетой; без такой
идентификации не добавляется в выборку трёх продуктов. Поле уровня 25 при
связи может быть дополнено продуктом анкеты, уровень 35 всегда собственный TAS.
Ключи нормализуются к -1; строки без обоих реальных заявочных ключей исключаются.
По дате применяется прежний отбор COALESCE(application_dt,parent_application_dt).
Читаются только необходимые для соединения/финала 17 полей. Даты и флаги TAS не агрегируются.

ШАГ 2.1 — Найденные пары

Конфликтующие строки самой TAS не скрываются; они видны при присоединении атрибутов и проверках.

КЛЮЧИ, ВЕРСИИ, РЕГЛАМЕНТ
-------------------------
История TQS имеет ключ questionnaire_rk + effective_from_dttm; несколько
версий RK нужны для исторического флага, это не дубли одной текущей анкеты.
Текущий срез должен иметь однозначное соответствие RK/ID/продукта.
TAS хранит последнее состояние по паре parent_application_rk/application_rk.
Три итоговых RK не NULL, отсутствующая сущность обозначается -1.

Начальная загрузка с 01.01.2025, далее ежедневно с начала прошлого квартала.
На 05.11.2026 начало предыдущего квартала — 01.07.2026. P_BEGIN_DATE задаётся ETL.
Прототип — расчётная выборка в sbx; целевой загрузчик сохраняет данные вне окна
и должен согласованно обрабатывать связи на границе окна. Сам прототип
не выполняет DELETE/INSERT производственной витрины.

ПРОВЕРКИ И СРАВНИМОСТЬ
---------------------
sql/check_internet_funnel.sql — отдельные SELECT. Анкетный знаменатель из
готовой TQS 1.2, заявочный — из TAS 1.5. Продукт анкеты и продукт заявки
не подменяют друг друга при подсчёте. NULL-продукт TAS — отдельная группа.
База КН/КК отличается от прежней RAW-цепочки: старые 701101 анкет и проценты
нужно пересчитать на новой базе, а не переносить как результат нового алгоритма.

Тесты работают при наличии ровно двух полей intention, без её дат/статусов/ФИО.
Проверяются все 20 исторических статусов TQS, текущие ID и исходная дата TQS,
анкеты без номера/без RAW, все номера анкеты, родительские ключи/источники,
авто, -1/NULL, собственный level35, остаток TAS, конфликтующие записи TAS,
продуктовые счётчики, периоды, точный атрибутивный состав и повторный запуск.
Банковская БД/Greenplum в этой среде недоступны; проверка офлайн синтетическая.
