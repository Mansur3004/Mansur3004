# Витрина статусов анкет и заявок

Весь SQL находится в одном файле:
[build_questionnaire_application_status.sql](sql/build_questionnaire_application_status.sql).
Над каждым блоком `drop table if exists ...; create table ...` подписаны
номер шага и его назначение. Старые скрипты удалены из текущей версии;
они остаются в истории Git.

## Порядок исполнения

| Блок | Содержание |
| --- | --- |
| 0 | Параметры: период, отчётный момент, режим связей КН/КК |
| 1 | Справочник статусов, история и общий флаг верификации, текущая когорта TQS |
| 2 | КН/КК: источник анкет с номером → BDM → TAS, сравнение прямого пути и УЗ |
| 3 | Авто: `questionnaire_id = application_id` |
| 4 | Единая витрина, покрытие и контроли сохранности |

Исполнять последовательно в одном подключении, с остановкой на ошибке.
Можно останавливаться на границах блоков и смотреть промежуточные результаты.
Диалект — Greenplum; хранение задано как в примерах: appendonly, column, zstd.
Рабочая схема — `sbx_pre_orb_fd`. Перед запуском проверить имена источников
в начале файла. Состав полей основан на присланных DDL; полные ФТ не получены.

Итоговая таблица:
`sbx_pre_orb_fd.prt_tech_questionnaire_application_status`.

## Правило верификации

Подтверждено пользователем: **любой выделенный зелёным или жёлтым статус
означает, что верификация была пройдена**. Цвета равнозначны.
`verification_flg = true`, если такой статус когда-либо был в доступной
истории анкеты до момента отчёта; иначе false. При отсутствующем RK флаг
остаётся NULL, а сама анкета сохраняется. Флаг агрегируется по
`(questionnaire_rk, src_cd)` до присоединения заявок.

В шаге 1.1 перечислены все 20 выделенных статусов, видимых на скриншотах:

- КН, `1376%`: `0`, `10.0`, `одобрено`, `CHECK_LIST_EMPTY`,
  `CHECK_LIST_ANTIFRAUD_OR_PRODUCT`.
- КК, `1383%`: `DONE`, `COURIER`.
- Авто, `1388%`: `APPROVE_RKK`, `APPROVED`, `PRE_APPROVED`, `APPROVE_CALL2`,
  `APPROVE_CALL3`, `ORDER_CREATED`, `VERIFICATION`, `DRIVER_CARD_ISSUE`,
  `DRIVER_CARD_ISSUE_UPLOADED`, `DOSSIER_UPLOADED`, `DEAL_VER`, `CREDIT_ISSUED`,
  `PRODUCT_BASKET_SIGNED`.

История не обрезается текущей версией или началом отчётного периода перед
расчётом флага. Текущий статус может быть другим — флаг останется true.
Полнота истории зависит от исходного ETL; при её усечении false означает
«статус не найден в доступных данных». Если на неприсланных частях листов
есть дополнительные выделения, они дополняются в одном справочнике шага 1.1.

## Связи и сохранность

У КН/КК номер берётся из `man_prt_tqs_questionnaire`, потому что в показанном
DDL технической TQS поля `application_num` нет. Мост сопоставляется с TQS
по `questionnaire_id` и точному `src_cd`; затем номер — с BDM.
Ключ BDM сравнивается с `tas.application_rk` для продуктового пути либо
с `tas.parent_application_rk` для УЗ с `parent_src_cd = 'MSSA'`.

УЗ без дочерней заявки, у которой `src_cd = NULL`, сохраняется отдельно.
Заглушки `-1` нормализуются в NULL до соединений. Несвязанные анкеты и
строки TAS остаются в результате. Пара, найденная прямым путём и через УЗ,
выводится один раз со списком обоих путей. Связи N:M явно отмечаются.
Строки с отсутствующими ключами сохраняются раздельно, без склейки по NULL.
Технические `q_entity_id`/`tas_entity_id` относятся к одной пересборке;
для связей с другими витринами использовать исходные RK и источники.

Режим КН/КК в шаге 0.1:

- `ALL` — исходный исследовательский режим: объединение кандидатов всех путей;
- `DIRECT` — только прямой продуктовый ключ;
- `UZ` — только пути через УЗ.

`prt_qas_kn_kk_link_quality` показывает покрытие и неоднозначность каждого
пути до выбора режима. Без результатов из банковской БД лучший путь ещё
не установлен. Режим ALL сохраняет найденные соответствия для исследования,
а не объявляет их автоматически подтверждёнными бизнес-связями.

Текущий срез TQS определяется по `effective_to_dttm` в дне `2999-12-31`.
Для TAS принято явное предположение об актуальном пересобираемом снимке:
поля окончания версии в DDL не показано. Если TAS версионная, реальный фильтр
нужно добавить в адаптеры 2.3 и 3.1. `processed_dttm` не заменяет актуальность.

Дата `2025-01-01` взята из прототипа. Если УЗ могла быть создана раньше
периода анкет, для диагностики можно отключить `bdm_limit_by_begin_date`.
NULL даты сохраняются и выводятся в контролях. Разные непустые атрибуты
на одном текущем ключе не выбираются произвольно: спорный атрибут — NULL,
конфликт виден в счётчиках, исходные строки остаются в промежуточных таблицах.

## Контроли и проверка

`prt_qas_checks`: все значения `error_count` должны быть 0. Проверяются
сохранность каждой анкеты и TAS-сущности, уникальность пары/флага и отсутствие
пустых итоговых строк. Отдельные отчёты показывают N:M и конфликты входов.
Ориентир 10% показывается по уникальным анкетам, сущностям TAS и их общей базе;
размножение строк соединением не увеличивает число связанных сущностей.

Локальная проверка: `python tests/validate_combined.py`, нужны `duckdb`
и `pglast`. Тесты проверяют все 20 статусов, историю и будущие записи,
обе ветки, режимы связей, точные покрытия, дубли, N:M, УЗ без дочки,
NULL/`-1`, конфликты атрибутов, пустые входы и повторный запуск.

Для тестового движка убираются только Greenplum-параметры хранения и
распределения, `btrim` задаётся через `trim`, момент отчёта фиксируется.
PostgreSQL-синтаксис проверяется отдельно. На банковских данных и самом
Greenplum скрипт в этой среде не выполнялся; планы и фактические имена
источников требуют проверки на месте.
