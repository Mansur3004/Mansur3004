# Витрина статусов анкет и заявок

Единый скрипт: [build_questionnaire_application_status.sql](sql/build_questionnaire_application_status.sql).
Все шаги подписаны над последовательными `drop table if exists` / `create table`.
В каждом запросе перечислены нужные атрибуты; `SELECT *` не используется.

## Цепочка данных

| Шаги | Обработка |
| --- | --- |
| 1.1–1.5 | RAW → безопасный разбор дат → фильтры тестовых данных → исходные приоритеты дублей → `prt_tqs_questionnaire` |
| 1.6–1.8 | Продукт и названия статусов → верификация по истории → представитель анкеты со всеми номерами заявок |
| 2.1–2.9 | Подготовленные анкеты КН/КК → `application_num` → `bdm.application` → TAS напрямую либо через УЗ |
| 3.0–3.4 | Подготовленные анкеты авто → TAS по `questionnaire_id = application_id` |
| 4 | Объединение веток, покрытие и контроли |

Единственный источник анкет —
`&p_db_rawd.v_sn_all_mart_dapp_prod_dm_dsa_cd_questionnaire_x_intention`.
Готовая `tech_questionnaire_status` и прежняя `man_prt_tqs_questionnaire`
не читаются. Обе продуктовые ветки продолжают подготовленную цепочку.
Новые источники заявок — `&p_db_bdm.application` и
`&db_sbx.tech_application_status`.

Диалект — Greenplum; параметры хранения соответствуют примерам:
appendonly, column, zstd. Исполнять последовательно с остановкой на ошибке.
Итог — `&db_sbx.prt_tech_questionnaire_application_status`.

## Макропеременные и продукт

В блоке 0.1 SQL перечислены все макропеременные и значения по умолчанию.
Таблиц параметров и справочника статусов нет. Значения подставляет ETL
или SQL-клиент перед выполнением: схемы без кавычек, строки/даты в одинарных
кавычках, числа и true/false без кавычек, списки строк через запятую
без внешних скобок. `&p_report_timestamp` фиксируется один раз на запуск.

RAW не содержит `level25_product_bp_nm`. Он формируется по `product_type_code`
через списки `&p_quest_product_kn_list`, `&p_quest_product_kk_list`,
`&p_quest_product_ak_list`. Названия задают `&p_prod_kn_name`,
`&p_prod_kk_name`, `&p_prod_auto_name`. Далее разделение анкет и расчёт
верификации используют `level25_product_bp_nm`.

По `q.src_cd` фильтров нет. `src_cd` и `src_cd_src` не определяют продукт;
источниковые OR-условия из старого прототипа удалены. `src_cd_src` остаётся
в исходном позднем критерии разрешения дублей, оба поля передаются как атрибуты.
Неизвестные и неоднозначно настроенные коды выводятся в диагностике 4.11.
Фильтры источников BDM/TAS сохранены для соответствующих систем заявок.

## Очистка и верификация

Восстановлены фильтры тестовых ФИО, порядок `COALESCE`, минимальная дата
анкеты, обе исходные даты начала статуса и полный видимый `ORDER BY`
для `ROW_NUMBER` по `(questionnaire_id, status)`. Для КК сохранено
исключение партнёрских ID заданной длины. Отличия от примера описаны
в SQL: некорректные календарные даты проверяются до `CAST`, а тестовые
шаблоны исключаются при совпадении хотя бы с одним из них.
Исходное `NOT LIKE ANY` этого не обеспечивало.

`verification_flg = true`, если в доступной очищенной истории анкеты
был любой отмеченный зелёным или жёлтым статус её продукта:

- КН: `0`, `10.0`, `одобрено`, `CHECK_LIST_EMPTY`, `CHECK_LIST_ANTIFRAUD_OR_PRODUCT`.
- КК: `DONE`, `COURIER`.
- Авто: `APPROVE_RKK`, `APPROVED`, `PRE_APPROVED`, `APPROVE_CALL2`,
  `APPROVE_CALL3`, `ORDER_CREATED`, `VERIFICATION`, `DRIVER_CARD_ISSUE`,
  `DRIVER_CARD_ISSUE_UPLOADED`, `DOSSIER_UPLOADED`, `DEAL_VER`, `CREDIT_ISSUED`,
  `PRODUCT_BASKET_SIGNED`.

Списки задаются тремя макропеременными `&p_*_verification_status`.
Флаг агрегируется по `(questionnaire_id, level25_product_bp_nm)`
до соединений и выбора представителя. Смена источника его не сбрасывает.
При отсутствии ID флаг NULL, такие строки сохраняются раздельно.
RK анкеты отсутствует в RAW и не выдумывается.

Нижняя граница RAW — `&p_rds_report_dt_date`, по умолчанию `2024-10-01`,
как в последнем примере. Когорта анкет ограничивается `&P_BEGIN_DATE`
после расчёта флага. Поэтому «когда-либо» относится к доступной истории
после исходных фильтров. Все номера из переживших дедупликацию статусов
сохраняются в `application_nums` и участвуют в соединении с BDM.

## Связи и допущения

КН/КК сопоставляются с BDM по точному `application_num`, затем с
`tas.application_rk` для прямого пути или `tas.parent_application_rk`
для УЗ. Режим `&p_kn_kk_link_mode`:

- `ALL` — объединение кандидатов всех путей для исследования;
- `DIRECT` — прямой продуктовый путь;
- `UZ` — пути через универсальную заявку.

Одна пара, найденная несколькими путями, выводится один раз со списком
путей. Связи N:M отмечаются. УЗ без дочерней заявки сохраняется отдельно,
заглушки `-1` переводятся в NULL перед соединениями. Несвязанные анкеты
и строки TAS входят в итог с пустой второй стороной.

Последующие шаги исходного ETL показаны не полностью. Представитель анкеты
выбирается по последнему времени записи, затем видимому приоритету
русского статуса КН. Это допущение указано в SQL; флаг и набор номеров
не ограничены выбранным представителем. Исходная дедупликация ID/status
сохранена; разные продукты на одном таком ключе проверяет отчёт 4.12.

TAS считается актуальным пересобираемым снимком: в показанном DDL
нет поля окончания версии. Если она версионная, нужен подтверждённый
фильтр в адаптерах 2.3 и 3.1. `processed_dttm` актуальность не заменяет.
BDM фильтруется по `effective_to_date = &p_max_date`; ограничение началом
периода отключается через `&p_bdm_limit_by_begin_date = false`.

Технические `q_entity_id` / `tas_entity_id` относятся к одной пересборке.
Для внешних связей нужны бизнес-ключи. Конфликтующие непустые атрибуты TAS
становятся NULL, конфликт отражается в счётчиках промежуточных таблиц.

## Проверка

`prt_qas_checks`: все `error_count` должны быть 0. Покрытие в
`prt_qas_coverage` считается по уникальным анкетам и сущностям TAS;
размножение строк не увеличивает число связанных сущностей.
`prt_qas_kn_kk_link_quality` сравнивает пути и неоднозначность.
Отчёты 4.10–4.12 показывают отбраковку RAW и проблемы классификации.

Локальный запуск: `python3 tests/validate_combined.py`, зависимости:
`duckdb`, `pglast`. Проверяется PostgreSQL-синтаксис после подстановки
макросов; исполнение на синтетических данных проверяет очистку дат/ФИО,
исходные приоритеты, все 20 статусов, общий источник нескольких продуктов,
смену источника, исторические номера, обе ветки, режимы связей, N:M,
NULL/`-1`, УЗ без дочки, конфликты, пустые входы и повторный запуск.
В тестовой БД отсутствуют готовая TQS и прежняя выборка анкет — скрипт
может получить анкеты только из RAW.

Для DuckDB убираются Greenplum-параметры хранения и распределения,
`btrim` задаётся через `trim`. На банковских данных и самом Greenplum
скрипт не выполнялся. Фактическое покрытие 10%, лучший путь через УЗ
и планы на рабочих объёмах требуют проверки в банковской среде.
