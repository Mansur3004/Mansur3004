# Витрина статусов анкет и заявок

Новый вариант по уточнённой логике: [build_internet_funnel_v2.sql](sql/build_internet_funnel_v2.sql).
КН/КК проходят исходную цепочку TQS из RAW, авто читается из готовой TQS.
[Пошаговая инструкция TXT](docs/prototype_v2_steps.txt) объясняет назначение,
происхождение и способ копирования каждого шага, с номерами строк нового SQL.
Результат — `&db_sbx.prt_if2_tech_internet_funnel`; таблицы с префиксом
`prt_if2_` не затрагивают результаты прежнего варианта.
Проверка: `/workspace/.venvs/qas/bin/python tests/validate_prototype_v2.py`.

Для уже построенной витрины есть [отдельный расчёт покрытия](sql/check_internet_funnel_coverage.sql).
Он заменяет запрос с несколькими `COUNT(DISTINCT ...)` после ошибки VMEM:
группировки анкет и заявок выполняются последовательно, затем считаются строки.
В `&p_funnel_table` задаётся фактическое полное имя готовой витрины; её пересборка
не требуется. Те же шаги включены в конец основного V2. Память на банковских
объёмах не измерена; квоты Greenplum скрипт не меняет.

Для выяснения причин сходимости добавлены [отдельные проверки](sql/diagnose_internet_funnel_coverage.sql)
и [пояснения к результатам](docs/funnel_coverage_diagnostics.txt). Они сравнивают
исходную базу TAS с тремя целевыми продуктами, выделяют УЗ, периоды и потери
связи на BDM/TAS. Раздел 1 работает по готовым итогу и TAS; последующие разделы
используют промежуточные таблицы того же запуска. Основной прототип не меняется.

Ниже описан предыдущий прототип: его SQL, тесты и каталог атрибутов сохранены.

[Единый SQL](sql/build_questionnaire_application_status.sql) восстанавливает
кредитную часть показанного ETL `tech_questionnaire_status`, сохраняет
`application_num`, получает настоящий `questionnaire_rk` и соединяет анкеты
с заявками. Все `drop/create` подписаны, атрибуты перечислены явно.

[Каталог атрибутов TXT](docs/attributes_catalog.txt) содержит происхождение
всех 19 итоговых полей, состав источников по доступным скриншотам и полный
список полей каждой из 35 создаваемых таблиц. Неизвестные части метаданных
отмечены отдельно; в конце указано, где получить их в DBeaver.

| Результат | Назначение |
| --- | --- |
| `&db_sbx.prt_tech_internet_funnel` | Ровно 19 бизнес-полей из запроса пользователя, с явными типами |
| `&db_sbx.prt_qas_funnel_detail` | Полные атрибуты обеих сторон, номера, статусы, источники, интервалы и диагностика связей |
| `&db_sbx.prt_qas_tech_questionnaire_status` | Восстановленная история: все 19 исходных атрибутов TQS, `application_num` и поля трассировки |

Рабочая схема по умолчанию — `sbx_pre_orb_fd`. Прежнее имя результата
`prt_tech_questionnaire_application_status` больше не используется и не
обновляется этим скриптом; читать новый итог, указанный выше.

## Порядок шагов

| Шаги | Цепочка |
| --- | --- |
| 1.1–1.5 | RAW → разбор дат → тестовые фильтры → исходные приоритеты дублей → `prt_tqs_questionnaire` |
| 1.6–1.9 | Исходная маршрутизация → ветки КК, КН, авто с константой продукта, названиями и приоритетами статусов |
| 1.10–1.12 | КН/авто: сдвиг одинаковых времён → общий поток с КК, `application_num` сохранён |
| 1.13–1.15 | Актуальные пары ID/RK → присоединение RK → интервалы статусов через `LEAD` |
| 1.16–1.17 | Верификация и все номера по истории → версия анкеты на отчётный момент |
| 2 | КН/КК: подготовленные номера → BDM → TAS, прямой путь и пути через УЗ |
| 3 | Авто: подготовленная анкета → TAS по `questionnaire_id = application_id` |
| 4 | Подробный результат → проекция 19 полей → покрытие и контроли |

Диалект — Greenplum; исполнение последовательно, с остановкой на ошибке.
Параметры хранения соответствуют примерам: appendonly, column, zstd.
Макропеременные, значения по умолчанию и правила подстановки перечислены
в блоке 0.1 SQL. Таблиц параметров и справочника верификации нет.
`&p_report_timestamp` — одно фиксированное значение на весь запуск.

## Происхождение продукта и RK

`level25_product_bp_nm` отсутствует в RAW. В исходном ETL продукт задаётся
константой внутри ветки: `&p_prod_kn_name`, `&p_prod_kk_name`,
`&p_prod_auto_name`. Вход в ветку использует исходное условие
`src_cd_src LIKE ... OR product_type_code IN (...)`. В КН дополнительно
исключается источник КК; в КК сохраняется ограничение длины ID.
Оба плеча OR восстановлены по новым полным скриншотам. Это не правило
«один источник — один продукт»: пересечения веток сохраняются и диагностируются.
После присвоения продукта фильтры анкет и верификация используют только
`level25_product_bp_nm`, без фильтра по `q.src_cd`.

В исходном UNION `src_cd_src` становится `src_cd` TQS; исходный RAW `src_cd`
сохранён отдельно как `raw_src_cd`. NULL в `src_cd_src NOT LIKE ...` ведёт
себя как в исходнике: строка не проходит ветку КН, даже если её код — КН.
Эти случаи видны в отчёте маршрутизации 4.11.

`questionnaire_rk` берётся из актуальных уникальных пар
`(questionnaire_id, questionnaire_rk)` таблицы
`&p_db_cdmr.tech_questionnaire_x_customer`, по умолчанию схема
`dm_pik_fd_cdmr`. Повторы одной пары из-за нескольких клиентов удаляются.
Разные RK одного ID сохраняются; отсутствие RK даёт NULL и диагностику.
Для сохранности несвязанных анкет исходный `INNER JOIN` заменён на `LEFT JOIN`.
`row_number()` используется только для служебных идентификаторов пересборки.

Пользователь подтвердил: под `tech_questionnaire_rk` имелся в виду
`tech_questionnaire_status` со скриншотов. Эта цепочка восстановлена,
включая последний JOIN с готовыми RK из `tech_questionnaire_x_customer`.
Дебетовые продукты, депозиты и текущие счета остаются вне задачи КН/КК/авто.

## История и сохранность

Сохранены исходные приоритеты очистки, `MIN` даты до дедупликации,
обе даты начала статуса, 47 приоритетов КН и 186 приоритетов авто
с отдельным значением 187 для NULL. По приоритетам сдвигаются совпавшие
времена КН/авто; затем `LEAD` строит окончания версий. Текущая версия
действует на `&p_report_timestamp`; выбор по последнему времени обработки
из прежнего прототипа удалён.

`quest_verification_flg` означает наличие любого выделенного зелёным
или жёлтым статуса в доступной истории своего продукта. Расчёт выполняется
до текущего среза, по RK + продукту; пока RK нет — по ID + продукту.
Пустые ID сохраняются отдельно с NULL флагом. Списки всех 20 статусов —
в трёх макропеременных в шапке SQL. История ограничена исходными фильтрами
и нижней границей RAW `&p_rds_report_dt_date`; это не обещание полной истории банка.

Все номера переживших исходную дедупликацию статусов остаются в
`application_nums`, разворачиваются и участвуют в соединении с BDM.
Прямой путь сравнивает BDM RK с `tas.application_rk`, путь УЗ — с
`tas.parent_application_rk`. Режим `&p_kn_kk_link_mode`: `ALL`, `DIRECT`, `UZ`.
Одна пара нескольких путей выводится один раз; N:M и УЗ без дочки сохраняются.
Несвязанные анкеты и строки TAS остаются с NULL второй стороной. Финальная
проекция не использует DISTINCT и не сокращает число строк detail.

Даты и заявочные флаги берутся из TAS. Для итогового уровня 25 приоритет
у TAS, при NULL используется продукт анкеты; обе версии и конфликт остаются
в detail. Пользователь подтвердил, что уровень 35 полностью повторяет
логику уровня 25: оба итоговых поля используют
`COALESCE(TAS.level25_product_bp_nm, TQS.level25_product_bp_nm)`, включая
анкеты без TAS. Исходный уровень 35 TAS сохранён в detail; отчёт 4.15
показывает расхождения исходных уровней, а контроль проверяет равенство итоговых.
`processed_dttm` — момент этой загрузки с типом `timestamp(0)`.

## Проверка и известные ограничения

[Тесты](tests/validate_combined.py) проверяют PostgreSQL-синтаксис и исполнение
на синтетической DuckDB: очистку, все статусы верификации, приоритеты и
интервалы, маршрутизацию, настоящий RK и его конфликты, исторические номера,
обе ветки, режимы связей, N:M, NULL/−1, УЗ без дочки, повторный запуск,
точный состав/типы/значения 19 итоговых полей и соответствие TXT всем таблицам.
Для DuckDB убираются Greenplum storage/distribution-параметры и добавляется
эквивалент `btrim` через `trim`.

Подготовленная среда: `/workspace/.venvs/qas/bin/python tests/validate_combined.py`.
Для другой среды нужны Python, `duckdb==1.5.6`, `pglast==8.7`.
Сами банковские источники и Greenplum в этой среде недоступны.

`prt_qas_checks`: все `error_count` должны быть 0. Отчёт 2.7 сравнивает пути
по покрытию и неоднозначности; 4.5 — покрытие уникальных сущностей, ориентир 10%.
Исследовательский режим ALL не доказывает правильность всех найденных связей.

Отличия и ограничения исходной логики описаны в SQL и TXT. В частности,
`EXTRACT(SECONDS FROM interval)` возвращает компонент секунд, а не полную
длительность. Исходная формула сохранена, отчёт 4.14 показывает затронутые
строки и неположительные интервалы. Даты проверяются до CAST; исходное
`NOT LIKE ANY` заменено исключением совпадения с любым тестовым шаблоном.
Равные времена в LEAD разрешаются дополнительными критериями порядка.

Для TAS пока предполагается актуальный снимок: в показанном DDL нет поля
окончания версии. Если TAS версионная, необходим подтверждённый фильтр
в адаптерах 2.3/3.1. `processed_dttm` не заменяет актуальность. Необходимые
метаданные и способы их получения перечислены в разделе 5 TXT.
