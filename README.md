# Объединение статусов анкет и заявок

Цель — проверить связи, затем построить витрину для автокредитов и КН/КК,
сохранив и анкеты без заявки, и заявки без анкеты. Рабочий диалект по
скриншотам — Greenplum. Подключения к банковской БД в этой среде нет.
SQL выполняет пользователь в своей БД; для продолжения достаточно
скриншотов агрегированных результатов. Копировать исходный код или данные
в чат не требуется.

## Порядок работы

1. **Проверить фактическую схему** — `sql/01_inventory.sql`.
   Уточнить реальные имена технических витрин, ключи, поле номера заявки,
   версионность и атрибуты верификации. Метаданные читаются без доступа к
   содержимому источников. Скриншоты показывают несколько вариантов имен
   (`tech_*`, `prot_tech_*`, `man_prt_tech_*`), поэтому не выбираем один молча.
2. **Проверить жизнеспособность первого участка через УЗ** —
   `sql/02_probe_uz.sql`. Он работает без TAS, используя существующую выборку
   `sbx_pre_orb_fd.man_prt_tqs_questionnaire`. Сравнить MSSA с прямыми
   продуктовыми источниками в одинаковой когорте. Проверить покрытия,
   неоднозначность номеров и прирост покрытия от УЗ. На полном объеме это
   существенные сканирования; сначала посмотреть планы загрузок.
3. **Проверить полные пути на уровне сущностей** —
   `sql/03_probe_full_paths.sql`, после результатов 1–2. Два имени технических
   витрин задаются в загрузках `*_q_raw` и `*_tas_raw`. Поля взяты из
   показанного DDL; фактический состав должен подтвердить этап 1.
   Скрипт сохраняет гипотезу об актуальности TAS как неподтвержденную.

   | Ветка | Кандидат связи | Ограничения источников |
   | --- | --- | --- |
   | Авто | `tqs.questionnaire_id = tas.application_id` | TQS: `1388%`, TAS: `ALPP`; проверить продукт |
   | КН, прямой | `q.application_num → bdm.application.application_num → application_rk = tas.application_rk` | TQS: `1376%`, BDM/TAS: `MSCL` |
   | КК, прямой | тот же путь по `tas.application_rk` | TQS: `1383%`, BDM/TAS: `CCPP_CRCA`, `CCPP_BATR` |
   | Через УЗ | `q.application_num → bdm.application` с `src_cd = 'MSSA'`, затем `application_rk = tas.application_rk` | TAS: `MSSA`; сравнить с родительским путем |
   | Через родителя УЗ | та же BDM-УЗ, затем `application_rk = tas.parent_application_rk` | `tas.parent_src_cd = 'MSSA'`; дочерний `tas.src_cd` по продукту |

   Родительский путь — гипотеза по наличию полей TAS, не подтвержденное
   описание ETL. Эти варианты сравниваются отдельно; объединять их в
   итоговую связь до проверки конфликтов нельзя. Источник ключа BDM должен
   соответствовать источнику соответствующего ключа TAS. Нельзя соединять
   разные источники только по совпадению текстового номера.

4. **Зафиксировать зерно и выбор способа связи.** Отдельно измерить уникальные
   анкеты, заявки, пары и степени связи. Выбрать путь по покрытию и качеству,
   а не только максимальному числу строк. Несколько продуктовых заявок у
   одной УЗ могут быть корректной связью 1:N. Связи N:M требуют объяснения;
   произвольный `row_number() = 1` не подходит. Если потребуются приоритеты
   путей, сохранить причины выбора и отвергнутые неоднозначные варианты.
5. **Собрать единую таблицу связей двух веток.** Сначала только идентификаторы,
   источники, тип пути и показатели неоднозначности. Одну и ту же пару,
   найденную несколькими путями, хранить один раз с сохранением происхождения.
   Приоритет прямого пути над УЗ возможен только после анализа конфликтов.
6. **Присоединить атрибуты и флаг верификации.** Расчет верификации оформить
   отдельно на ключе анкеты, затем присоединить к TQS. Уровень проверки
   (анкета/клиент), момент проверки, допустимые статусы и поведение при
   отсутствии сведений определяются ФТ. Фрагмента ФТ пока нет. `valid_flg`,
   `gosuslugi_flg`, финальное одобрение и сам факт связи не считаются
   верификацией без такого правила. Неизвестное значение не заменять на `false`.
7. **Собрать итог и проверить сохранность.** Явный список полей с префиксами
   `q_`/`app_`, без `select *`. Связанные пары + анкеты без пары + заявки без
   пары через `UNION ALL` и `NOT EXISTS` либо корректный `FULL OUTER JOIN`.
   Фильтры источников/актуальности применять к входам до внешнего соединения.
   Проверить, что каждая входная сущность присутствует в результате, нет
   повторов пары и пропавших несвязанных строк, флаг не размножает строки.

Следующие этапы будут отдельными последовательными блоками
`drop table if exists ...; create table ... as ...;`. Менять после уточнения
схемы нужно будет входные слои, а не всю логику сборки.

## Что уже известно и где предположения

- `bdm.application.effective_to_date` подтверждено; на скриншотах фильтр
  `DATE '2999-12-31'` и `application_begin_date >= DATE '2025-01-01'`.
- В показанном DDL TQS есть `effective_from_dttm` и `effective_to_dttm`.
  Предварительный фильтр текущего среза:
  `tqs.effective_to_dttm >= TIMESTAMP '2999-12-31 00:00:00'
  AND tqs.effective_to_dttm < TIMESTAMP '3000-01-01 00:00:00'`.
  Проверить реальные значения границы; исторические статусы этим срезом
  не покрываются. Нужен ответ из ФТ, требуется ли история или текущий срез.
- В показанном DDL TAS поля окончания действия нет. Есть `processed_dttm`,
  но это не доказательство версионности. Гипотеза: TAS — пересобираемый
  актуальный снимок. Если подтвердится, дополнительный фильтр версии не
  нужен. Если есть поле `effective_to_dttm`, применить аналогичный фильтр
  в отдельном входном слое TAS. Нельзя молча выбирать максимальное время
  обработки по всей таблице или последнюю строку на заявку.
- `application_num` есть в сыром источнике и промежуточной выборке анкет,
  но отсутствует в показанном DDL TQS. Для второго пути потребуется мост
  TQS ↔ номер заявки, с проверкой `(questionnaire_id, src_cd)` и периодов.
   Промежуточную выборку нельзя объявлять самой TQS или заменять ею знаменатель
   покрытия итоговой витрины. На этапе 2А это только доступный диагностический
   источник; этап 2Б уже считает знаменатель по ключам технической TQS.
- PK TQS на скриншоте содержит `questionnaire_rk`, `effective_from_dttm`;
  PK TAS — `parent_application_rk`, `application_rk`. Фактическую уникальность,
  роль `src_cd` и допустимость NULL в родительском ключе нужно проверить.
- Префиксы источников из макросов: авто — `1388%`; КН — `1376%`;
  КК — `1383%`; УЗ — `MSSA`; авто-заявки — `ALPP`; КН-заявки — `MSCL`;
  КК-заявки — `CCPP_CRCA` и `CCPP_BATR`. Классификацию продукта нужно
  подтвердить распределениями, особенно для нескольких продуктов в источнике.
- Начало периода `2025-01-01` в этапе 2 взято из прототипа, не из ФТ.
  Не вводим ограничение размера выборки: первые N строк дают смещенное покрытие.

## Как оценивать 10%

Основная предварительная метрика этапа 2А:
`100 × число анкет, имеющих хотя бы одну связь BDM / все пригодные анкеты
выбранной ветки`. Анкеты без номера заявки остаются в знаменателе.
Пустые идентификаторы/источники учитываются отдельным контролем.

В полном пути отдельно потребуются:

- покрытие анкет TQS: связанные уникальные анкеты / все анкеты когорты;
- покрытие заявок TAS: связанные уникальные заявки / все заявки когорты;
- объединенное покрытие сущностей: (связанные анкеты + связанные заявки) /
  (все анкеты + все заявки);
- число связанных пар и связи 1:1, 1:N, N:1, N:M.

Пока трактовка «10% от всей базы» не уточнена, показываем все три покрытия
без объявления приемки. Отдельно нужны итоги авто, КН, КК и общий взвешенный
итог. Доля строк `INNER JOIN` от строк `FULL JOIN` способна расти из-за N:M,
поэтому не подходит как единственное доказательство.

Числа со скриншота (1 236 245 строк соединения и 58 148 383 строк исходной
выборки) сами по себе не доказывают покрытие уникальных анкет. Сравнивать
их с 10% до согласования зерна некорректно.

## Что выполнить сейчас и что прислать

1. Выполнить `sql/01_inventory.sql`; прислать результаты 1–3, особенно
   реальные TQS/TAS, `application_num`, поля актуальности и верификации.
2. Если `man_prt_tqs_questionnaire` существует с указанными полями, выполнить
   `sql/02_probe_uz.sql`; прислать результат 1, распределение продуктов
   (результат 2) и сводку пересечения путей (результат 7).
3. После проверки имен и полей выполнить `sql/03_probe_full_paths.sql`.
   Главный результат — отчет 1; дополнительно нужны контроли повторов
   (2–3), полноты (4), продуктов (5) и пересечения путей (6).
4. Прислать скриншот ФТ про флаг верификации и состав/зерно итоговой витрины.
   Ключи клиентов, ФИО и реальные номера заявок не нужны.

Если SQL останавливается с ошибкой, достаточно скриншота текста ошибки
и названия выполнявшегося блока. Ни доступ к БД, ни успех полного пути,
ни корректность флага верификации на реальных данных пока не подтверждены.

## Локальная проверка

`tests/validate_diagnostics.py` проверяет синтаксис PostgreSQL через `pglast`
и исполняет запросы в DuckDB на искусственных таблицах. При этом удаляется
только Greenplum-специфичная конструкция `DISTRIBUTED RANDOMLY`, а в тестовом
движке регистрируется эквивалент однопараметрической функции `btrim`.

Проверены точные покрытия, сохранение анкет без номера в знаменателе,
повторные статусы, неоднозначные номера, разделение источников, NULL в
родителе, текущие/исторические строки TQS, различие УЗ и родительского пути,
контроль N:M, пустые входы и повторяемость двух последовательных запусков.
Планы Greenplum, права, реальные объемы и бизнес-смысл связей этим тестом
не подтверждаются. Финальная витрина и флаг верификации пока не реализованы:
они зависят от результатов диагностики и недостающего фрагмента ФТ.
