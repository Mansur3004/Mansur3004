# Верификация анкеты → КН/КК → автокредиты

Актуальный порядок: сначала общий флаг верификации анкеты, затем связь
КН/КК через номер заявки и BDM, только после неё — автокредиты по ID.
Подключения к банковской БД в этой среде нет. Достаточно скриншотов
агрегированных результатов; персональные данные в чат не нужны.

## Что подготовлено сейчас

1. [status_by_product.sql](sql/status_by_product.sql) — пять кандидатов
   статусов, восстановленных из жёлтой заливки на скриншотах.
2. [01_questionnaire_verification.sql](sql/workflow/01_questionnaire_verification.sql)
   — самостоятельный расчётный слой верификации без заявок и BDM.
3. [script_steps.md](docs/script_steps.md) — последовательные шаги общего
   блока, затем КН/КК, затем авто и итоговой сборки в формате примеров.

SQL оформлен как последовательные `drop table if exists ...; create table
... with (...) as ... distributed randomly;`. Диалект — Greenplum.
Рабочая схема `sbx_pre_orb_fd` и имя `tech_questionnaire_status` взяты
со скриншотов; фактические имена и типы надо проверить перед запуском.

## Этап 1: общий флаг

Выполнить `sql/status_by_product.sql`, затем
`sql/workflow/01_questionnaire_verification.sql`. На первом запуске правила
оставлены неподтверждёнными: `verification_flg` имеет NULL, а отдельный
`verification_candidate_flg` показывает срабатывание рабочей гипотезы.
Это позволяет исследовать статусы без объявления одобрения/выдачи
подтверждённой верификацией.

Кандидаты: КН — `одобрено`, `CHECK_LIST_EMPTY`; КК — `DONE`; авто —
`VERIFICATION`, `DEAL_VER`. Они выбраны по жёлтой заливке, смысл которой
ещё нужно подтвердить. Самих исходных файлов status_by_product в репозитории
нет; сохранена только явно видимая информация со скриншотов.

Рабочая семантика — «хотя бы раз достиг выбранного статуса». Предусмотрен
режим текущего статуса. Успешное завершение проверки требует отдельного
согласованного списка положительных статусов. История не обрезается
фильтром текущей версии до расчёта признака.

Выход — `sbx_pre_orb_fd.prt_qs_verification_flags`: одна строка на
`(questionnaire_rk, src_cd)`, с флагом, кандидатом, причиной решения и
моментом отчёта. Этот результат позже присоединяется к обеим веткам.
Отсутствие статуса в неполной истории не считается доказательством false.

Для продолжения нужны смысл флага и значение цветовой разметки.
Если формула из ФТ отличается, меняем справочник/политику до написания
веток, сохраняя общий ключ и интерфейс результата.

## Следующие этапы

Пока это последовательный план, а не реализованный итоговый SQL:

- КН/КК: источник `questionnaire_status.application_num` →
  `bdm.application.application_num` → `application_rk` → TAS;
  сравнить продуктовый путь и родительский путь через УЗ.
- Авто: `questionnaire_id = application_id`, с отдельными фильтрами
  источников/продукта и проверкой актуальности.
- Обе ветки используют общий флаг и сохраняют анкеты и заявки без пары.

Новые скриншоты TAS показывают строки УЗ без дочерней заявки:
`application_rk = -1`, дочерний `src_cd = NULL`, источник УЗ хранится
в `parent_src_cd`. Их нельзя терять фильтром дочернего источника или
соединять друг с другом по `-1`. Подробности — в плане этапа КН/КК.

## Ранние диагностические скрипты

`sql/01_inventory.sql`, `sql/02_probe_uz.sql` и `sql/03_probe_full_paths.sql`
сохранены как прежние исследовательские материалы. Они не задают новый
порядок исполнения. В частности, адаптер TAS в `03_probe_full_paths.sql`
потребует пересмотра с учётом новых скриншотов перед этапом КН/КК.
[Ранний план](docs/previous_diagnostics.md) сохранён отдельно.

## Локальная проверка

`tests/validate_verification.py` проверяет новый общий слой на искусственных
данных: историю и текущий статус, будущие версии, NULL и false, полноту
истории, продукт/источник, конфликт ключа, дубли и повторный запуск.
`tests/validate_diagnostics.py` относится к прежним диагностическим скриптам.

Для обоих тестов нужны `duckdb` и `pglast`. Для локального движка удаляются
только Greenplum-конструкции распределения/хранения, а `btrim` задаётся через
эквивалент `trim`. PostgreSQL-синтаксис проверяется отдельно. Это не проверка
на реальной БД, не подтверждение ФТ и не проверка планов Greenplum.
